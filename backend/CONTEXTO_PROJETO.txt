Estado atual
------------
- Projeto Maven criado e compilando.
- Package principal: Application.PediJa
- Entidades criadas em src/main/java/Application/PediJa/Entities.
- Enums atuais: OrderStatus e PaymentMethod.
- Chave composta criada em Entities/PK/OrderItemPK.java.
- Migration atual: src/main/resources/db/migration/V1__initial_schema.sql.
- A migration V1 cria todas as tabelas de uma vez: usuario, cliente, produto, pedido e item_pedido.
- Isso difere do planejamento, que previa migrations V1 a V5 separadas. Manter essa diferença registrada para decisão posterior.
- Timestamps das entidades usam LocalDateTime, compatível conceitualmente com TIMESTAMP da migration.
- Última validação: mvn test -DskipTests executado com BUILD SUCCESS.
- Repositories criados em src/main/java/Application/PediJa/Repositories: ClientRepository, ProductRepository, OrderRepository, OrderItemRepository e UserRepository.
- UserRepository possui o método findByLogin(String login), previsto para a autenticação.
- DTOs de request/response criados em src/main/java/Application/PediJa/Dto para User, Client, Product, Order e OrderItem.
- RequestOrder recebe clienteId, paymentMethod e uma lista de items; não recebe status, precoUnitario ou valorTotal.
- RequestOrderItem recebe somente produtoId e quantidade, com validações @NotNull e @Positive.
- ResponseOrder contém os dados do pedido, valorTotal e a lista de ResponseOrderItem.
- ResponseOrderItem expõe produtoId, produtoNome, quantidade, precoUnitario e subtotal. O subtotal é calculado no service e não é persistido como coluna própria.

Entidades e tabelas
-------------------
- User -> usuario
  - id, login, password mapeado para senha, dataCriacao mapeado para data_criacao.
- Client -> cliente
  - id, nome, cpf, telefone, email, endereco, dataCadastro mapeado para data_cadastro.
  - possui lista de Order com mappedBy = client.
- Product -> produto
  - id, nome, descricao, preco, estoque.
- Order -> pedido
  - id, client, dataPedido, orderStatus mapeado para status, paymentMethod mapeado para forma_pagamento, valorTotal e items.
  - relacionamento ManyToOne com Client.
  - relacionamento OneToMany com OrderItem.
- OrderItem -> item_pedido
  - id composto, pedido, produto, quantidade e precoUnitario mapeado para preco_unitario.
  - usa EmbeddedId e MapsId.
- OrderItemPK
  - pedidoId mapeado para pedido_id.
  - produtoId mapeado para produto_id.

Atualizações recentes
---------------------
- A camada de DTOs separa os contratos de entrada e saída das entidades JPA.
- O frontend deverá listar produtos usando ResponseProduct, exibindo o nome e mantendo o id internamente para enviar produtoId no pedido.
- A listagem de itens de um pedido pode usar GET /orders/{orderId}/items; nesse caso, pedidoId não precisa estar em cada ResponseOrderItem.
- O status inicial do pedido deve ser definido pelo service ou pelo domínio como PENDENTE; o DEFAULT da migration permanece como fallback.
- Permanecem pendentes a criação de Role, o alinhamento final entre constraints da migration e Bean Validation, e a correção do nome do setter setProutoNome em ResponseOrderItem.

Regras essenciais
-----------------
- BigDecimal para dinheiro.
- O preço unitário do item deve ser copiado do produto no momento da venda.
- O valor total deve ser calculado no backend.
- Entidades não devem ser expostas diretamente como contrato da API; usar DTOs.
- Bean Validation cuida de formato/estrutura; Service cuida das regras de negócio.
- Senhas nunca devem ser armazenadas em texto puro.
- A chave de item_pedido é (pedido_id, produto_id); o mesmo produto deve ser consolidado no pedido.
- Recursos inexistentes devem gerar ResourceNotFoundException.
- Regras inválidas devem gerar BusinessException.
